# 多帳號威脅模型與安全不變式

- 狀態：HM-00 起草（2026-11-14）。HM-18 把已知限制與事故處理寫進產品 DOCS。
- 來源：計畫 §8.1、§8.2、§8.9、§8.10（repo 外）；決策見 `decisions.md`（DQ-37 採 (a)：接受同 uid 信任邊界並寫明）。
- 契約與差異表：`contract.md`；不變式對應的測試檔：`acceptance-matrix.md` 的測試檔登記表。

## 結論

1. 帳號之間的隔離靠三件事：只看 token 選帳號、每帳號一個子程式（只收自己帳號的 bearer）、每帳號自己的名額與額度。
2. **同 uid 是同一個信任邊界**：管理程序與所有子程式都是 uid 10001。一個子程式被攻破，等於整個 add-on 所有帳號被完全控制，
   包括留後門。這和 PaaS 相同；README 與 DOCS 不宣稱子程式之間隔離。
3. 13 條不變式（I1～I13）每一條都有測試與負責片；I8、I9、I10、I13 是審查後加嚴的。

## 1. 角色與信任邊界（計畫 §8.1）

| 角色 | 能做什麼 | 設計要擋什麼 |
|---|---|---|
| 持有某帳號 token 的 MCP 用戶端（含拿到外洩網址的人） | 呼叫該帳號的工具 | 碰不到別的帳號（I1～I4）；拖垮不了別的帳號，**含預設帳號的持有人**（I8） |
| HA 非管理員（能開 Ingress） | 看到面板入口 | 管理 API 一律 403；探測不到任何帳號狀態（I10） |
| HA 管理員 | 管理全部帳號 | 信任；文件寫明「任何 HA 管理員都能看、輪替、刪除每個帳號的權杖」 |
| 子程式（第三方 MCP server） | 用自己帳號的後端憑證 | 只拿到自己帳號的環境（白名單）；port 錯置時不能執行別帳號的請求（I4） |
| 同 uid 的本機程序（含被攻破的子程式） | 見下方 | **已知限制**（DQ-37） |
| 拿到備份檔的人 | 看到全部帳號的 token 與後端帳密 | 文件建議加密備份；還原不讓舊 token 復活（I9）；token 不進備份是後續選項（DQ-46） |
| 有 HA 還原權的人 | 把資料換回備份當時 | 還原＝撤銷事件（I9）；開關關的版本也一樣（I13） |
| 後端（Odoo、Nextcloud…） | 以來源 IP 節流 | 一個帳號的錯誤不連累同後端其他帳號（認證退避，`contract.md` 第 7 節） |

### 同 uid 信任邊界

- 管理程序與所有子程式都是 uid 10001；只有管理程序設成 non-dumpable。
- 一個子程式被攻破＝**整個 add-on 所有帳號被完全控制，包括留後門**：
  - 讀任何帳號的 state（0600 防不了同 uid），拿到全部 token 與後端帳密。
  - 改任何帳號的 state：植入自己知道的 token、打開寫入權限、把後端網址改到自己的伺服器，下次重啟就收到憑證。
  - 改 `profiles.json`。
  - 別的帳號的 port 空出來時先綁住：Supervisor 一 spawn 就標 running，閘道會把 B 的 child bearer 與 B 用戶端的參數送給它；
    HM-15（條件式）之前沒有擋。
  - 對同 uid 的程序送訊號，停掉別的子程式或管理程序。
- 兄弟子程式讀得到彼此的 `/proc/<pid>/environ`；`os.environ.pop` 擋不住，所以子程式 bearer 不靠「讀完就從環境變數拿掉」。
- 加固選項：Landlock 在 HAOS 預期不可用（核心設定只有 AppArmor）；add-on 自帶 AppArmor 設定檔是後續選項，可行性未確認，不在本計畫。
- 決定（DQ-37 採 (a)，2026-11-14）：接受並寫明；加事故處理（第 4 節）。

## 2. 安全不變式（計畫 §8.2）

| 不變式 | 做法 | 測試 | 切片 |
|---|---|---|---|
| I1 MCP 請求屬於哪個帳號只由 token 決定 | 分派器只解析路徑 token 或 Bearer；不讀標頭、cookie、query | 31 種網址變形、冒用；交叉案例「Bearer 屬於 B」與「密鑰路徑屬於 A＋`Authorization` 屬於 B」：密鑰路徑上絕不改看 `Authorization` | HM-01、HM-08 |
| I2 一把 token 最多屬於一個帳號 | 建立一律新 token 與 child_token；全部比完；2 個以上 503 | 複製帳號目錄造成撞號 → 503、不導向 | HM-07、HM-08 |
| I3 撤銷、輪替、刪除只影響該帳號、立即生效 | 每帳號 TokenAccess；刪除順序（先撤銷再停子程式、最後移出索引） | 負載中輪替 B，A 的串流不斷；刪除後舊 token 立即 404／401 | HM-05、HM-08、HM-10 |
| I4 A 的請求只會被 A 的子程式執行 | 每帳號一個子程式；spawn 前 port 檢查；子程式只收自己帳號的 bearer 並驗格式；listener 檢查（條件式） | 直連 loopback：不帶、帶錯、帶別帳號、兩個標頭、空字串都 401；別的程序先綁 port → 不轉發 | HM-06、HM-09、HM-15 |
| I5 新帳號不借用別人的身分、權限不比預設寬 | 連線全空；複製預設帳號當下的政策（DQ-02 採 (a)） | 新帳號呼叫工具回 `backend_not_configured`；政策等於預設當下值 | HM-07、HM-10 |
| I6 預設帳號資料不被多帳號功能寫入 | 索引與帳號目錄放旁邊 | 啟動、列清單、建刪帳號前後預設 `state.json` SHA-256 不變 | HM-01、HM-07 |
| I7 紀錄不含 token、帳號名稱、路徑 | 新 log 只寫 id 前 8 碼、port、pid；遮罩不比 pin 版 PaaS 差 | 測試期間收集所有 log record，掃 token 與名稱 0 命中 | HM-01、HM-02、各片 |
| **I8 一個帳號（含預設帳號）的持有人拖垮不了其他帳號** | 每帳號准入、位元組額度、轉送名額、串流上限、待送回覆額度、httpx client；回覆處理依帳號輪流；健康檢查連兩次失敗才判壞 | S5、S6；預設帳號送 64 條慢速 16 MiB body＋大回覆時，閒置的額外帳號仍 200、無 OOM；CPU 飢餓；慢讀 RSS（`contract.md` 第 6 節） | HM-08、HM-14、HM-30、HM-19c |
| **I9 還原不讓任何帳號的舊 token 復活**（涵蓋：含 HM-13 的版本以後做的備份；預設帳號依 DQ-03） | 兩訊號偵測；以磁碟為準撤銷；讀不到就隔離；獨立驗證；不受開關管 | root 擁有的還原樹；sentinel 不符；每一步中途當掉重做；讀不到的 state 之後任何開機都不被路由；C1-M1 攻擊序；版本混搭 | HM-13a、HM-13b、HM-13c |
| **I10 先驗 HA 管理員，才做任何看帳號狀態的判斷；非管理員在任何帳號狀態下拿到逐位元相同的 403** | 共用管線，角色檢查在第 ⑥ 步（`contract.md` 第 3.2 節） | 路由表自動產生的否定矩陣 | HM-10 |
| I11 Odoo token 永遠綁一個後端身分（DQ-40 ⑩ 採用：擴到 Nextcloud、Hermes 的使用者欄位） | 換身分欄位時同一次寫入換 token | 舊 token 兩條入口都失效；只換密碼不換 | HM-12（HM-22、HM-24） |
| I12 開通後沒明確選帳號的管理請求不會落到任何帳號 | 缺 `X-MCP-Profile` 回 400；回聲比對 | 缺標頭的 reveal、rotate、bootstrap 都 400（管理員）；回聲不符面板不顯示 | HM-10、HM-11 |
| **I13 沒開通的產品（含緊急關閉版）不讓休眠帳號的 token 可用** | 休眠處理：開機在 listener 前撤銷額外帳號與孤兒 | 開關關＋有帳號資料 → 全部撤銷；重新開通後未核對前不能重發 | HM-13b |

## 3. 已知限制（計畫 §8.9；HM-18 寫進文件）

- 同 uid＝同一個信任邊界；一個子程式被攻破＝整個 add-on 所有帳號被完全控制。紅隊三項（對別帳號 port 的 SSRF、讀檔或 `/proc`、
  單帳號 OOM）在隔離的 QA HAOS、經使用者授權才做（DQ-34，HM-29）。
- 沒有 cgroup 時，OOM 可能先殺管理程序，所有帳號一起斷；額外帳號子程式的 `oom_score_adj`＝500 只是讓核心傾向先殺它們，不是保證。
- 備份含全部帳號的秘密；建議加密備份；token 不進備份是後續選項（DQ-46）。
- 還原守門只涵蓋含 HM-13 的版本以後做的備份；回退（還原升級前備份）之後再升級不會自動撤銷，要按「全部撤銷」。
- 偵測依賴「檔案層級還原會產生新檔」與「Supervisor 以 root 放回」；整份資料以檔案層級搬移也會被當成還原（方向安全：多撤銷）。
- 面板 403（Core 未審）時，任何帳號都撤銷不了，只能停止整個 add-on。
- 緊急關閉要發一版，推估一個工作天以上；期間只能停 add-on 或在面板撤銷。
- HA Core 與 Supervisor 會自動更新；平台假設（UC-08、UC-10、sentinel）每次發版重驗並記版本。

## 4. 事故處理：懷疑某個子程式或帳號被攻破（計畫 §8.10；HM-18 寫進 DOCS）

1. 止血：面板「全部撤銷」；面板打不開（403）就停止 add-on。
2. 在每個後端換掉該 add-on 用的密碼或 key（全部帳號都要，因為同 uid 讀得到全部），再到面板逐帳號存新憑證。
3. 檢查每個帳號的政策（寫入開關、停用工具、逐項授權、禁止的操作）與後端網址有沒有被改。
4. 檢查 `profiles.json` 與 `profiles/` 有沒有多出來的帳號或隔離目錄（面板清單）。
5. 必要時還原「事故前」的備份（守門會撤銷 token），在核對卡逐帳號核對後重發。
6. 留證：add-on log（只含 id 前 8 碼）與診斷頁；不要貼 token 或密碼。
