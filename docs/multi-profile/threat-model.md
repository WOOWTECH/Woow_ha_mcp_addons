## 結論

1. 帳號之間的隔離靠三件事：只看 token 選帳號、每帳號一個子程式（只收自己帳號的 bearer）、每帳號自己的名額與額度。
2. **同 uid 是同一個信任邊界**：管理程序與所有子程式都是 uid 10001。一個子程式被攻破，等於整個 add-on 所有帳號被完全控制，
   包括留後門。這和 PaaS 相同；README 與 DOCS 不宣稱子程式之間隔離。
3. 13 條不變式（I1～I13）每一條都有測試與負責片；I8、I9、I10、I13 是審查後加嚴的。

## 1. 角色與信任邊界（計畫 §8.1）

| 角色 | 能做什麼 | 設計要擋什麼 |
|---|---|---|
| 持有某帳號 token 的 MCP 用戶端（含拿到外洩網址的人） | 呼叫該帳號的工具 | 碰不到別的帳號（I1～I4）；拖垮不了別的帳號，**含預設帳號的持有人**（I8） |
| HA 非管理員（能開 Ingress） | 看到面板入口 | 管理 API 一律 403；探測不到任何帳號狀態（I10） |
| HA 管理員 | 管理全部帳號 | 信任；文件寫明「任何 HA 管理員都能看、輪替、刪除每個帳號的權杖」 |
| 子程式（第三方 MCP server） | 用自己帳號的後端憑證 | 只拿到自己帳號的環境（白名單）；port 錯置時不能執行別帳號的請求（I4） |
| 同 uid 的本機程序（含被攻破的子程式） | 見下方 | **已知限制**（DQ-37） |
| 拿到備份檔的人 | 看到全部帳號的 token 與後端帳密 | 文件建議加密備份；還原不讓舊 token 復活（I9）；token 不進備份是後續選項（DQ-46） |
| 有 HA 還原權的人 | 把資料換回備份當時 | 還原＝撤銷事件（I9）；開關關的版本也一樣（I13） |
| 後端（Odoo、Nextcloud…） | 以來源 IP 節流 | 一個帳號的錯誤不連累同後端其他帳號（認證退避，`contract.md` 第 7 節） |

### 同 uid 信任邊界

- 管理程序與所有子程式都是 uid 10001；只有管理程序設成 non-dumpable。
- 一個子程式被攻破＝**整個 add-on 所有帳號被完全控制，包括留後門**：
  - 讀任何帳號的 state（0600 防不了同 uid），拿到全部 token 與後端帳密。
  - 改任何帳號的 state：植入自己知道的 token、打開寫入權限、把後端網址改到自己的伺服器，下次重啟就收到憑證。
  - 改 `profiles.json`。
  - 別的帳號的 port 空出來時先綁住：Supervisor 一 spawn 就標 running，閘道會把 B 的 child bearer 與 B 用戶端的參數送給它；
    HM-15（條件式）之前沒有擋。
  - 對同 uid 的程序送訊號，停掉別的子程式或管理程序。
- 兄弟子程式讀得到彼此的 `/proc/<pid>/environ`；`os.environ.pop` 擋不住，所以子程式 bearer 不靠「讀完就從環境變數拿掉」。
- 加固選項：Landlock 在 HAOS 預期不可用（核心設定只有 AppArmor）；add-on 自帶 AppArmor 設定檔是後續選項，可行性未確認，不在本計畫。
- 決定（DQ-37 採 (a)，2026-11-14）：接受並寫明；加事故處理（第 4 節）。

## 3. 已知限制（計畫 §8.9；HM-18 寫進文件）

- 同 uid＝同一個信任邊界；一個子程式被攻破＝整個 add-on 所有帳號被完全控制。紅隊三項（對別帳號 port 的 SSRF、讀檔或 `/proc`、
  單帳號 OOM）在隔離的 QA HAOS、經使用者授權才做（DQ-34，HM-29）。
- 沒有 cgroup 時，OOM 可能先殺管理程序，所有帳號一起斷；額外帳號子程式的 `oom_score_adj`＝500 只是讓核心傾向先殺它們，不是保證。
- 每帳號隔離在請求層，不在連線層：8081 外框（64＋32×產品上限）是全 add-on 共用的連線數，閒置的 keep-alive 連線、沒帶 token 的連線也算。
  任何人（含沒有 token 的人）開滿連線，之後每個人的新連線都拿到 uvicorn 純文字 503（既有，G2 S7；HM-08 審查 S-5 實測）。要不要給外框
  加餘裕或加第一個請求的讀取逾時，留給後續。
- 位元組預算管的是大請求的位元組（收到與轉送兩者較大的，扣到請求結束），不是記憶體。HA 閘道自己（**不含子程式**）一個請求的記憶體高峰是
  扣款的 2.6～4.3 倍（16 MiB 的 ASCII、中文、emoji 字串）、14 倍（ASCII 大字串夾一個 emoji）、27.6 倍（約 0.8 MiB、元素接近 20 萬的結構）
  （HM-31 審查 E2，`contract.md` 第 5 節）；子程式還要再解析一次。HM-31 起每個產品都有 JSON 結構守門（巢狀 64 層、元素 20 萬個，不受開關管），
  HM-08 量到的 24 倍（16 MiB 的 `[{},{},…]` 解析約 390 MiB）不再出現，但守門上限內最壞的結構一個請求仍約 21 MiB、扣款不到 1 MiB：同時大量
  這種請求的總量只由准入（開通）或 8081 外框 64（沒開通）限住，最壞約 64×21 MiB≈1.3 GiB（推算）。公式用的放大倍數 20 是 PaaS 閘道＋子程式
  的實測；HA 的倍數待 HM-19c，超過 20 就回功能 PR 改（`contract.md` 第 5 節的放行條件）。
- 全 add-on 的位元組預算是帳號之間共用的（PaaS #155 同）：每個帳號最多用到自己的份額（min(64 MiB, max(16 MiB, 預算÷2))）。預算夠大時要兩個
  帳號才能一起把它用光，這時第三個帳號超過 64 KiB 的請求拿 `-32003`。**預算落在下限 16 MiB 時，一個帳號的份額就是整份預算**：一個帳號扣著一個
  大請求（tools/call 最長 330 秒，SSE 到串流結束），其他帳號所有超過 64 KiB 的請求都拿 `-32003`（HM-31 審查 S-1）。開通的 Odoo 在 MemAvailable
  約 1.4 GiB 以下都在下限，約 1.7 GiB 以下份額超過預算的一半；PaaS 的 1 GiB pod 一樣（PaaS 已知限制 (6)、(9)）。小請求不受影響。要不要給開通的
  產品加下限或份額上限，交主對話或 HM-19c 決定（`contract.md` 第 5 節）。PaaS 的已知限制「涓流上傳佔住預算」在 HA 最多 60 秒（整體讀取上限）、
  閒置 30 秒就放棄，都要有效的 token。
- 位元組預算的推導（`contract.md` 第 5 節）：HA 的 add-on 沒有 Pod 記憶體上限，用開機那一刻的 MemAvailable 減 256 MiB（HA Core 還沒載完時
  偏高）；之後 HA Core 與其他 add-on 用掉更多時，預算不會跟著縮小。同一台機器裝了多個 WOOW add-on 時，每個都拿同一份 MemAvailable 推導，
  等於重複計算（HM-31 審查 S-5）。預算全滿時閘道用到「預算×實際的放大倍數」（上兩條），可能壓縮到別的程式；HM-19c 量測後決定要不要只取
  MemAvailable 的一部分，或依同機的 WOOW add-on 數分攤。
- 結構守門的慢路徑與 JSON 解析都在事件迴圈裡同步跑（PaaS 同；HM-31 審查 S-3）：上限內、元素接近 20 萬的 body，掃描約 0.1 秒（0.76 MiB 的
  `{"a":1}` 119 ms、0.29 MiB 的 `[]` 104 ms；解析另 40／8 ms），閘道處理一個這種請求的 CPU 從約 78／12 ms 變成 197／115 ms（本機 AMD EPYC
  7713，審查 E3）。一個 token 每秒送約 5～9 個這種請求就吃滿事件迴圈，8081 所有帳號與 8099 一起變慢。HM-19c 在 J6412 量；優化（例如一次處理
  連續的結構字元）列為回補 PaaS 的題目。
- 同時帶 `Content-Length` 與 `Transfer-Encoding: chunked` 的請求（HM-31 審查 MF-1）：h11 0.16.0（HA 的 HTTP 解析器，沒有 httptools）照 chunked
  讀；閘道把這時的 `Content-Length` 當成沒宣告，照實際收到的位元組扣預算、看閒置（`contract.md` 第 2.4 節、§9 #108）。RFC 9112 §6.1 另要求伺服器
  回應這種請求後關閉連線；依 h11 0.16.0 與 uvicorn 0.38.0 的原始碼，它們不關（既有，和 HM-31 無關）。只有前面另有一層照 `Content-Length` 切請求、
  又重用後端連線的代理時，才有請求走私的風險。要不要直接回 400 並關連線（會改單帳號回應），交主對話決定。
- 小請求（收到與轉送都 ≤64 KiB）不扣預算、也不受讀取閒置逾時（只有整體 60 秒）：同時開著很多條讀取中的小請求連線沒有個數上限，由准入
  （開通）與 8081 外框限住（PaaS 已知限制 (2)，同樣適用）。准入滿時讀進來的小請求也一樣（2 秒、64 KiB）。
- 位元組預算放不下的大請求先讀完丟掉再回答（PaaS：讓先送完內容才讀回應的用戶端看得到回答）：丟的期間佔著一條連線（開通的產品也佔著准入），
  最多閒置 30 秒、整體 60 秒；只留頭尾各 4 KiB，不佔記憶體。
- 不接受 UTF-16／32 的請求內容（MCP 規格的傳輸是 UTF-8，已知的用戶端都沒送過）；帶 `charset=utf-16` 的用戶端會被拒（PaaS 同）。
- 排隊中的斷線監看只認「那個請求的連線被關掉」（HM-14；PaaS `docs/mcp-gateway-limits.md` 的已知限制，19f36e2、`091dfbc`）。MCP SDK 層級的
  請求逾時與取消（只送 `notifications/cancelled`）、MCP Python SDK 2.3.0 預設 `terminate_on_close=True` 的關閉路徑（離開 transport 先送
  DELETE 並等回應，DELETE 排在那個 POST 後面，POST 的連線一直開著）都看不到：排隊中的寫入在名額空出後照樣被執行（HA 最多等 1 秒，等不到
  就回 `-32003`、不送出）。`terminate_on_close=False` 或 HTTP 層逾時就關連線的用戶端，寫入會被丟掉。後續可做（不在 HM-14）：同一個 session
  的 `notifications/cancelled` 或 DELETE 到達時丟掉它排隊中的請求。
- 准入滿時（一般名額和它的佇列都滿）：HM-31 起 ≤64 KiB 的 POST 仍讀進來，只有通知或回應的照常處理，`notifications/initialized` 經保留名額
  送到（HM-14 審查 MF-2 (b)，2026-11-16 定案；`contract.md` 第 2.4 節、§8.8 #96）。還在的限制：這時剛連上的用戶端的 initialize（帶 id 的請求）
  拿忙碌回應（200＋`-32003`），要等准入有空位才連得上；大於 64 KiB 或 2 秒內讀不完的通知拿 503。只影響同一個帳號自己。
- 子程式處理到一半斷線時，用戶端拿到 `-32004`：操作可能已完成也可能沒有，要先確認再重試（HM-14）；子程式停止了時，只有看門狗會自己
  再起它（退避中、正在起、新世代）才說「會自動重新啟動」，被擋下、失敗、已停止或沒有設定時說「目前沒有在重新啟動」（§8.8 #100）。token 換掉時，
  標頭已送出的一次送完 JSON 回覆不能改，閘道關掉連線（用戶端看到不完整的回應）；SSE 會補 `-32005`（`contract.md` 第 2.5 節、§8.8 #92）。
- 備份含全部帳號的秘密；建議加密備份；token 不進備份是後續選項（DQ-46）。
- 還原守門只涵蓋含 HM-13 的版本以後做的備份；回退（還原升級前備份）之後再升級不會自動撤銷，要按「全部撤銷」。
- 偵測依賴「檔案層級還原會產生新檔」與「Supervisor 以 root 放回」；整份資料以檔案層級搬移也會被當成還原（方向安全：多撤銷）。
- 面板 403（Core 未審）時，任何帳號都撤銷不了，只能停止整個 add-on。
- 緊急關閉要發一版，推估一個工作天以上；期間只能停 add-on 或在面板撤銷。
- HA Core 與 Supervisor 會自動更新；平台假設（UC-08、UC-10、sentinel）每次發版重驗並記版本。
- 後端網址拒絕 loopback（HM-20，產品開通後）只看 127.0.0.0/8、::1 與 `localhost` 這類名稱（DQ-10 的範圍）。add-on 自己的
  主機名與 Supervisor bridge 位址不在規則裡：從那裡只連得到 8081 與 8099（子程式只聽 127.0.0.1）；8081 要 token，8099 只收
  `172.30.32.2`，所以最多是把這個帳號的後端憑證送進自己的閘道或面板、拿到 401、403 或 404。要連 bridge 位址一起擋，是另一個
  決定，不在 HM-20。

## 4. 事故處理：懷疑某個子程式或帳號被攻破（計畫 §8.10；HM-18 寫進 DOCS）

1. 止血：面板「全部撤銷」；面板打不開（403）就停止 add-on。
2. 在每個後端換掉該 add-on 用的密碼或 key（全部帳號都要，因為同 uid 讀得到全部），再到面板逐帳號存新憑證。
3. 檢查每個帳號的政策（寫入開關、停用工具、逐項授權、禁止的操作）與後端網址有沒有被改。
4. 檢查 `profiles.json` 與 `profiles/` 有沒有多出來的帳號或隔離目錄（面板清單）。
5. 必要時還原「事故前」的備份（守門會撤銷 token），在核對卡逐帳號核對後重發。
6. 留證：add-on log（只含 id 前 8 碼）與診斷頁；不要貼 token 或密碼。
