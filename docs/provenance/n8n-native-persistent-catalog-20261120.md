# n8n persistent catalogs require native SQLite

Based on #129 `3f54ae2b3c015c08c76545fb38807fe1199261c0`. n8n-mcp 2.96.2 falls back from `better-sqlite3` to sql.js if native loading or opening fails. The sql.js adapter periodically writes the whole database directly and logs save failures; it cannot provide the persistent catalog durability expected by #129. Its HTTP process also starts listening before it initializes a database for the first MCP session.

When `NODE_DB_PATH` names a persistent catalog, the n8n-only `backend_policy.cjs` preload opens that existing file using the real native binding before the child listener starts. It reads the schema and verifies writable access with a no-row update inside a rolled-back transaction. Missing, unreadable, corrupt, read-only or unloadable native catalogs fail with a fixed message without creating a replacement or exposing the database path. This check does not replace the existing parent-side validation, backup, recovery or schema policy. Once started, the composed, exact-digest `fix_fts_probe_temp.py` patch makes the upstream adapter refuse native failure rather than falling back to sql.js; this also covers failures after the preflight. Direct nonpersistent `:memory:` use retains upstream fallback behavior. The parent prepares and supplies `NODE_DB_PATH` for its persistent children; a direct upstream invocation without that variable keeps its prior behavior.

Tests exercise the actual Node 26 child with simulated missing module and failing native binding, assert it exits before listening, never loads sql.js, and preserves catalog bytes; they also exercise an actual native child through MCP initialize, a failure after a successful native preflight, nonexistent/empty/corrupt/read-only paths, the normal nonpersistent fallback, and an unchanged catalog after a successful preflight. No image or HAOS system is involved. This does not promise persistence when storage fails after successful writes, or automatically repair an existing damaged catalog.
