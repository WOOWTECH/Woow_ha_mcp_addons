# n8n FTS capability probe crash safety

Based on #129 `16ec351afed362c93fe444bd29e1802cf8adf376`. Published n8n-mcp 2.96.2 `database-adapter.js` SHA-256 `ce43947010501c11eb4fd9fede6ed20e2202233dc1954c8de1345f20df936388` has two identical FTS capability probes (better-sqlite3 and sql.js). Both created and dropped `test_fts5` in the main schema. Abrupt termination between the two statements could leave a virtual table and its shadow tables, which the existing strict catalog schema rejects on restart. The unqualified DROP could also remove an existing main table of that name.

The build patch `apps/n8n/patches/fix_fts_probe_temp.py` accepts only that exact source or the reviewed result `b0bfa44960b9109b383b2c467ed9f1155f38d972a2c5ef7b403ce0caeb9e060c`, changes both CREATE and DROP statements to `temp.test_fts5`, and fails closed on drift. Docker and CI installation apply it; `backend_policy.cjs` verifies the patched source before the n8n server loads. The strict persistent catalog schema validation is unchanged. Already persisted unexpected tables are not automatically removed.

The Node 26.12.1 regression invokes the real native adapter and kills the process with SIGKILL immediately after CREATE, then compares the complete main `sqlite_schema` before and after. It verifies normal support and preservation of a same-named main table and its data. The pinned sql.js build lacks FTS5; its normal result is tested as unsupported. For its crash-path namespace test, the real adapter's SQL execution is instrumented to emulate the unavailable FTS CREATE with an ordinary table in the requested namespace and force an export before SIGKILL; this checks the fallback adapter's namespace and persistence behavior, not real FTS5 support. Test databases and credentials are synthetic; no image or live system is used.
